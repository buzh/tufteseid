# UI review, live site, 2026-10-06

Driven against `https://kart.scheen.no` in headless Chrome, signed in as the
`test@te.st` account (no spots, `inviteQuota` 0, plain `user`) and as a guest in
a clean browser context. Code references were checked against `main` at
`04725d17`.

A note on the data: of 78 public spots, **5 have evidence and 34 have a
footprint**. Several findings below are only reachable because most of the
register predates the rectangle rule, which makes them *more* likely for a
visitor, not less.

Transient. Delete this file when the findings have been triaged.

## Reproduced live

### 1. A share link to a footprint-less spot never moves the map

`/l/372AEX` opens the reader with the map still wherever the recipient last
left it — at a cold start, the whole-country zoom 3. The spot is not on screen
and nothing says where it is.

`src/spots/shareLink.ts:97-112` skips its centring animation whenever a reading
is open, on the stated grounds that `EvidenceReader` fits the footprint
instead. `src/evidence/EvidenceReader.tsx:141-157` early-returns
`if (!footprint)`. The repair that would give the spot one lives only in
`SpotCard` (`src/spotControls/SpotCard.tsx:194-203`), which is never mounted for
a reader who is not the owner or an admin — the gate is in
`spotReadingAtom`'s getter, `src/spots/atoms.ts:103-109`.

So the spot is never repaired *for* a visitor and never fitted *to* them.
Verified both sides: `/l/SNDXFR` (footprint, no evidence) centres correctly;
`/l/372AEX` (neither) does not. **44 of the 78 public spots are in this state.**

### 2. `?backgroundLayer=` is silently rewritten

Loading
`?lon=206400&lat=6566050&zoom=16&backgroundLayer=lidarHillshade` lands on
`backgroundLayer=lidarCvat` within a few seconds. Reproduced on a brand-new
browser profile with empty `localStorage`, so it is not a remembered
preference. It happens wherever a per-project LiDAR flight covers the viewport
(≤ 1 m/px, i.e. zoom ≥ 15); at zoom 3 the parameter survives.

The chain: Automatisk is `halved(true)` with no URL representation
(`…/backgroundLayers/lidarAuto.ts:5`), its override effect
(`src/lidarControls/useLidarControls.ts:216-241`) moves the half onto the
flight, and `preferredLidarRender`
(`…/backgroundLayers/lidarProjects.ts:108-114`) upgrades **exactly**
`skyggerelieff` to `cvat` — the one value a URL-requested `lidarHillshade`
implies. `backgroundLayerAtomEffect` (`…/backgroundLayers/atoms.ts:140`) then
mirrors the result back to the URL.

The fidelity mechanism for this already exists: `selectProject(p, wanted)` /
`selectNational(wanted)` take the `resolveLidarStyle` clamp instead of the
upgrade, added so a recorded render reproduces verbatim (commit `c3f7ca1`).
**`wanted` has no caller anywhere in `src/`** — every call site passes one
argument.

Smallest fix: have `getDefaultBackgroundLayer` report that the parameter was
present and seed `lidarAutoDatasetHalves` to `false` when it was. Or add `auto`
to the `UrlParameter` union so the state is expressible at all.

### 3. The last Kulturminner filter is effectively unreachable

`src/heritageControls/HeritageMenu.tsx:89` —
`<ScrollArea.Autosize mah={420} type="scroll">`. On a 900 px-tall viewport the
content is 504 px: "Uten vern" is cut in half and **"Uavklart vernestatus" is
entirely below the fold**, with ~400 px of empty screen underneath the menu.

It does scroll by wheel, but `type="scroll"` keeps the scrollbar
`display: none` until a scroll is already in progress, so there is no
affordance that anything is below. Measured: viewport `scrollHeight` 504,
`clientHeight` 420, both scrollbars `data-state="hidden"`.

`type="auto"` would at least show the bar, and `mah` could key off the
available height rather than a constant.

### 4. Hints float above modals and stay clickable

The `Hint` popover renders at `z-index: 300`; Mantine's Modal overlay is `200`.
With the Invitasjoner dialog open, `elementFromPoint` on the TIPS "Greit"
button returns the button — it is the topmost element and live — while every
other surface is correctly blocked by the scrim. A hint anchored to a
centre-of-ribbon control would land on top of the dialog's own content.

### 5. The empty-evidence state is the wrong way round

`src/evidence/EvidenceGallery.tsx:274` puts the whole block — the "Bilder"
heading *and* the "drag the handle to reorder, the first is the cover" hint —
behind `rows.length > 0`. A brand-new spot's card therefore shows an empty
11 px strip where its main workspace will be.

`EvidenceReader` does have an "Ingen bilder ennå." empty state. It is shown
only to a reader who cannot add one. The owner, who could press the camera,
gets silence.

### 6. A new spot's rectangle row has no label

`src/spotControls/SpotProperties.tsx:138` falls back to `''` when
`footprintSideMetres` is null, which is the entire life of a new spot — the
first box every user ever sees. The row renders as a bare icon and an "Endre"
button with no text between them, directly under a labelled "Legg til skisse".

Compounding it, the pin row's button and this one are both named exactly
"Endre" with nothing to tell them apart.

### 7. A dead share link says nothing

`?lok=ZZZZZZ` signed in: `console.warn('[spots] no spot for code', …)`, the
parameter is stripped, and the app sits at the default view
(`src/spots/shareLink.ts:62-69`). Nothing on screen. The reader cannot tell
whether the link was mistyped, the spot was deleted, or it is private to
someone else. The signed-*out* path is handled properly — it raises the
sign-in dialog with `authPrompt = 'spotLink'` and keeps the parameter for the
retry.

### 8. Signed-out voting is a dead end

`src/spots/VoteControl.tsx:70-92` renders disabled thumbs under a correctly
span-wrapped tooltip reading "Logg inn for å stemme" — and offers no way to do
that. `cast` returns early on `!user` and the module does not import
`isAuthDialogOpenAtom`. The two other "needs an account" affordances both open
the dialog: `SpotToggle.tsx:39`, `SpotMenu.tsx:163`.

### 9. A comparison cannot be shared

Neither the view mode, nor the curtain position, nor the B half's ground has a
URL parameter. With the curtain open the address bar is unchanged, so "Kopier
lenke til visningen" hands over a single-ground link. For an app built around
reading one ground against another this is the most surprising gap in the URL.

## Narrow viewports — the app is desktop-only

Three `@media` rules exist in all of `src/`, all `max-width: 768px`, all
nudging a bottom-docked bar clear of the scale bar. No Mantine breakpoints, no
`useMediaQuery`, no `breakpoints` in `src/ui/theme.ts`.

### 10. The sign-in button is off-screen below ~900 px

Measured at 768 px: band `scrollWidth` 874 vs `clientWidth` 768, with
**Mine lokaliteter, Kopier lenke and Kontoen din all past the right edge**. At
390 px only the ground switch and one or two LiDAR chips remain — view mode,
Kulturminner, terrain, spots, share and sign-in all require discovering a
horizontal swipe along a 51 px strip. Turning on compare mounts a second ground
section and makes it worse.

`.tools` carries a `position: sticky` meant to prevent exactly this
(`src/ribbon/Ribbon.module.css:61-71`), but its containing block is the third
`1fr` grid item, which in an overflowing grid resolves to its own min-content
width — zero travel, so it pins nothing.

### 11. The reader's caption collapses before its sliders do

At 390 px the caption box measures **11 px** while the two transparency sliders
keep 64 and 54 px. `src/ui/Panel.module.css:82-89` gives `.footer` no
`min-width: 0` and no overflow handling, and the footer's children carry hard
`min-width` floors (`EvidenceReader.module.css:200,207,214`) totalling more
than the panel's cap. The one thing identifying which of 19 pictures you are
looking at is the first thing to go.

### 12. Touch input is sound; touch targets are not

Worth recording as a positive: every drag in the app is Pointer Events with
`setPointerCapture` and `touch-action: none` — the gallery reorder, the
curtain, the rectangle handles all work with a finger. But the rectangle corner
hit radius is 14 px (`src/map/rectAdjust.ts:28`), the reader's resize grip is
16 px, and the gallery drag handle is unsized. Also `startDrag`
(`EvidenceGallery.tsx:204-205`) checks `event.button` but not `event.isPrimary`,
unlike `useFloatingPanel.ts:182` and `CompareCurtain.tsx:55`.

## Accessibility

### 13. The map cannot be reached by keyboard

`#map` and `.ol-viewport` both have no `tabindex`. The complete tab order is 27
controls and none of them is the map, so a keyboard-only user can toggle every
layer and never pan or zoom. This also makes the gallery handle's documented
guard against "the press reaching OpenLayers' keyboard pan"
(`docs/architecture.md`) moot — nothing can focus the viewport in the first
place.

### 14. Heritage metadata chips are invisible to assistive tech

`MetaChip` (`src/heritageInfo/HeritagePopup.tsx:22-39`) wraps an `aria-hidden`
icon and a bare value in a hover `Tooltip`. No `aria-label`, no
`aria-describedby`, no `tabindex`. The "19" chip on Omsland gravfelt is
announced as "19" with no indication it counts enkeltminner, and a keyboard
user cannot summon the tooltip at all.

### 15. Tooltips on directly-disabled buttons never open

`src/spotControls/SpotCard.tsx:99-107`, `:126-135`, `:136-145` wrap `Tooltip`
straight around a disabled `ControlButton`, which dispatches no pointer events.
The same file uses the `<span>` idiom correctly at `:261-263`, as do
`EvidenceReader.tsx:197-199` and `VoteControl.tsx:68-71`, each with a comment
explaining why. Net effect: with a null footprint the elevation and camera
buttons are grey and mute.

### 16. Smaller ones

- The cover star is purely visual — nothing in the a11y tree says which
  picture is the cover.
- A focusable span with an empty accessible name in the heritage popup's head
  (`_kindIcon_`) — a tab stop that announces nothing.
- Mantine sliders expose `aria-valuetext=""`, so units are dropped.
- The account menu opens focus onto an unnamed generic.

## Copy and i18n

### 17. "Innattatt" / "Utatatt"

`src/locales/nb/translation.json:305-306`, the collapse/expand control on every
panel header. Neither looks like a Norwegian word in any variety — they read as
mangled "inn att" / "ut att". Your call, since the app's register is
deliberately colloquial elsewhere ("Vekk"), but these two stand out.

### 18. The ribbon calls an existing spot "the new one"

Opening the cogwheel on a saved spot puts the ribbon's `+` into a pressed state
and relabels the index button "Legg fra deg den **nye** lokaliteten for å bla i
lokalitetene". It is an edit, not a new spot.

### 19. The discussion thread is the one un-themed surface

English chrome, US dates ("9/30/2026 at 11:42 AM"), and remark42's teal against
the app's papaya.

I checked the claim in `src/talk/SpotTalk.tsx:3-4` and **it is accurate** — the
deployed bundle's locale list is `ar be bg bp cs de es fa fi fr he it ja ko mk
pl ro ru sv th tr ua vi zh zh-tw`, with no Norwegian or Danish. So `en` is a
real constraint, not an oversight. Worth considering `sv` anyway: it would give
`2026-09-30`-shaped dates and a Scandinavian register, both closer to right
than American English. The colour clash is separately fixable — the widget is
in our own DOM.

### 20. The i18n machinery is fully wired and completely inert

425 keys in `nb`, 9 each in `nn` and `en` (2.1 %). No language switcher, no URL
parameter, no `changeLanguage` call anywhere, and `navigator` deliberately left
out of the detection order (`src/i18n.ts:14-17`) so `Accept-Language: en` gets
100 % Bokmål. Nothing is broken — `fallbackLng: 'nb'` and that omission are
belt and braces. But the stubs will drift, and `npm run lint`'s locale check is
a JSON parse only, so nothing would catch it. Either fill them before adding
detection, or drop `supportedLngs` to `['nb']`.

## Code-level, not reproduced live

- `SpotCard.tsx:201` and `:209` — `.then(setActive)` with no liveness guard.
  Closing the spot or opening another while the PATCH is in flight re-opens the
  old one. Every comparable async path in the codebase does guard.
- `SpotCard.tsx:293-301` — the visibility switch is disabled on `busy` but not
  on `draft != null`, breaking the write-serialisation invariant the same file
  states two blocks earlier for the repair write.
- `SpotCard.tsx:194` — the one-write repair guard is a ref, so it dies with the
  component; the card unmounts on every trip to the microscope, the reading or
  the thread, re-firing the PATCH.
- Boot fetches `spots`, `spotScores` and `votes` at `perPage=1000` **twice** —
  the `auth-refresh` POST re-triggers the whole load. Cheap at 78 spots.

## Checked and fine

Recording these so they are not re-investigated:

- The footprint repair is correctly gated — no 403 storm, no failed PATCH in
  the network log for a non-owner.
- The heritage popup auto-pans the map to stay in view when it would overflow.
  (The clipping I first saw at 1024 px was a resize artefact: autoPan runs on
  open, not on resize.)
- `Icon` is `aria-hidden="true"` — icon ligatures are not announced.
- The talk button's disabled tooltip ("Diskusjonstråd er ikke tilgjengelig for
  upubliserte lokaliteter") works correctly.
- `useFloatingPanel`'s drag clamping is careful and correct, including the
  degenerate box-wider-than-map case and a resize listener that pulls a dragged
  box back on-map.
- The ribbon's height holds at 51 px when it overflows, at least on Linux
  Chrome with overlay scrollbars. The risk that an inline scrollbar grows the
  band and breaks the frozen sketch transform is real on platforms with classic
  scrollbars but did not reproduce here.
- `e4MSTP` in the gallery is the blend's real published name, not a missing
  label.
- Spot creation, naming from the place-name register, footprint derivation,
  terrain analysis, keeping evidence, and cascade delete all worked end to end.
- The heritage popup is the strongest surface in the app — the Askeladden and
  Kulturminnesøk links, the vern/datering chips and the "Mer" expander are
  exactly right.
